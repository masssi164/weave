# Boards Provider Spikes: Vikunja, OpenProject, Nextcloud Deck

Status: post-Release-1 spike artifacts  
Date: 2026-05-14  
Scope: issues [#119](https://github.com/masssi164/weave/issues/119), [#120](https://github.com/masssi164/weave/issues/120), and [#121](https://github.com/masssi164/weave/issues/121)

## Decision matrix

| Provider | Role | Recommendation | Main adapter implication |
| --- | --- | --- | --- |
| Vikunja | First strategic task-engine adapter candidate | Keep as first implementation candidate | Build a backend adapter that normalizes Vikunja projects/views/buckets/tasks into Weave projects/boards/columns/tasks. |
| OpenProject | Accessibility and mature workflow benchmark | Keep benchmark-only for now | Copy accessibility and workflow requirements, not OpenProject's full work-package product model. |
| Nextcloud Deck | Low-friction bridge adapter, fallback, or import path | Build only as bridge/import/fallback after Vikunja | Reuse Nextcloud auth/session direction, but translate Deck board/stack/card vocabulary and do not expose Deck as the Weave product model. |

Machine-readable contract fixture: [boards-provider-capability-matrix.json](boards-provider-capability-matrix.json).

## Adapter contract additions

These spikes keep the existing provider-neutral domain contract and add three concrete requirements for future adapter work:

- Every adapter declares a machine-readable capability matrix before Flutter can expose provider-specific states.
- Provider vocabulary is normalized at the adapter boundary: `project`, `board`, `column/list/status`, `task/card`, `label`, `comment/activity`, `attachment/link`, and `provider_sync_metadata`.
- Flutter may keep hidden preview fixtures, but provider auth, pagination, sync cursors, webhook validation, export/import, and support-safe error translation belong behind a backend or connector adapter.

Minimum capability keys are enforced by `test/architecture/boards_provider_capability_matrix_contract_test.dart`:

- `projects_boards`
- `columns`
- `tasks_cards`
- `comments`
- `labels`

- `incremental_sync`
- `webhook_events`
- `export_portability`
- `non_drag_ui_baseline`
- `provider_neutral_mapping`
- `backend_adapter_required`

## #119 Vikunja spike

### API/auth fit

- Vikunja exposes autogenerated Swagger/OpenAPI docs at `/api/v1/docs` and a machine-readable spec at `/api/v1/docs.json`.
- Auth fit is good: Vikunja recommends API tokens in the `Authorization: Bearer <token>` header; self-hosted instances can also use `/api/v1/login` for JWT, while Vikunja Cloud requires API tokens.
- The OpenAPI surface includes projects, project views/buckets, tasks, task comments, task labels, task assignees, task attachments, webhooks, and user export endpoints.
- Pagination is explicit on list endpoints such as projects via `page` and `per_page` parameters.

### Domain mapping

| Vikunja concept/API area | Weave concept | Adapter note |
| --- | --- | --- |
| Project | Workspace/project or board grouping | Preserve external project id in `provider_refs`. |
| Project view + bucket | Board + column/list/status | Use Weave `semantic_status`; do not leak bucket names as the only status model. |
| Task | Task/card | Map `title`, `description`, `done`, `priority`, `percent_done`, `start_date`, `due_date`, `end_date`, `position`, `labels`, `assignees`, and `attachments`. |
| Comments/reactions | Comment/activity | Sanitize rich text and expose screen-reader-safe activity summaries. |
| Labels | Label/tag | Color remains decorative; text label is authoritative. |
| Attachments | Attachment/link | Keep file ownership and external URLs in metadata. |
| Webhooks | Normalized events | Runtime spike must verify payload shape, retry, ordering, idempotency, and redaction. |
| Export endpoints | Portability/export | Strong fit for data-sovereignty story; verify restore/import separately. |

### Sync/event fit

- Webhook endpoints and event discovery are present, so Vikunja is the strongest first candidate for provider-pushed changes.
- Incremental sync still needs verification against update timestamps, webhook delivery guarantees, and conflict behavior.
- The adapter must emit Weave `TaskBoardEvent` envelopes; Flutter should only receive normalized state and capability readiness.

### Deployment/licensing/accessibility

- Deployment fit is good for self-hosting: Vikunja ships as one binary/container and supports SQLite, PostgreSQL, MySQL/MariaDB, Docker, packages, Kubernetes, and Ansible paths.
- Licensing needs explicit product review: most of the repository is AGPL-3.0-or-later, with desktop content GPL-3.0-or-later.
- Accessibility cannot be inherited from Vikunja's UI. Weave must own keyboard movement, screen-reader announcements, focus order, non-color status, and text scaling.

### Recommendation

Vikunja remains the first implementation candidate for a real provider adapter, but only behind a backend/connector boundary. Safe Flutter work before that is limited to provider-neutral preview fixtures, capability labels, and tests.

## #120 OpenProject accessibility benchmark

### Benchmark findings

- OpenProject's own accessibility checklist targets WCAG 2.1 Level AA and explicitly calls for logical reading/navigation order, text labels for inputs, color not being the sole signal, visible keyboard focus, keyboard-operable functionality, no focus traps, informative labels/headings, and doubled text remaining readable and functional.
- OpenProject boards are mature workflow surfaces: boards contain lists/columns and cards/work packages; action boards can map lists to status, assignee, version, subproject, or parent-child workflow changes.
- OpenProject docs describe card movement primarily via drag-and-drop, while also offering card detail/split-screen and direct status changes. Weave therefore must not treat drag-and-drop as sufficient.
- The API v3 work-package model is broader than Weave's first task slice: HATEOAS links include update/delete/move, attachments, assignee/responsible, priority, status, type, relations, watchers, comments/activities, parent/children, custom actions, custom fields, and optimistic locking via `lockVersion`.

### Weave UI requirements to copy

- Board reading order is deterministic: board summary, column heading/count, task title, status, assignee, due date, priority, conflict/sync state, then actions.
- Every movement must have non-drag alternatives: move up/down, move to column/status, mark blocked, mark done, assign, and archive.
- Focus never jumps unpredictably after create/update/move/delete; if the card moves, focus lands on the moved card or an explicit confirmation.
- Status, priority, overdue, blocked, and permission states are text/semantic states first; color is decorative.
- Screen-reader announcements cover create, update, move, failed move, sync conflict, permission denied, and offline queue states.
- Text scaling must keep primary task actions reachable; no card action may require hover or pointer precision.

### Recommendation

Keep OpenProject benchmark-only for now. Open a later provider spike only if Weave needs mature project-management workflows such as work-package hierarchy, custom fields, relations, time/cost, or enterprise workflow rules.

## #121 Nextcloud Deck bridge spike

### API/auth fit

- Deck's REST API is under `index.php/apps/deck/api/v1.0`; requests require `OCS-APIRequest: true` and JSON content type except attachment upload, which uses multipart form data.
- Auth/session fit is plausible because Deck is a Nextcloud app and Weave already has a Nextcloud integration direction, but the adapter must still avoid direct Flutter coupling to Deck endpoints.
- API coverage includes boards, ACLs, stacks, cards, labels, assignment/unassignment, card reorder, archive/unarchive, attachments, comments, import endpoints, calendar config, and deleted-object restore paths.
- Deck documents global 400 validation and 403 permission errors; these map cleanly to support-safe Weave errors.

### Domain mapping and gaps

| Deck concept/API area | Weave concept | Gap category | Adapter note |
| --- | --- | --- | --- |
| Board | Board/project grouping | product-model | Do not name the product surface Deck. |
| Stack | Column/list/status | product-model | Preserve order and archived/deleted state. |
| Card | Task/card | API | Map title, description, due date, order, archived, labels, assignees, attachments, comments. |
| Labels | Label/tag | accessibility | Color must be decorative, not semantic. |
| Assigned users | Assignee refs | auth/product | Normalize Nextcloud user ids/display names. |
| Attachments | Attachment/link | API/auth | File ownership and permissions must be explicit. |
| Comments | Comment/activity | API | Long imported comments may become attachments, so imports need loss notes. |
| ETag + If-Modified-Since | Incremental sync metadata | sync/event | Polling-friendly; no documented push-event contract in the Deck API docs reviewed. |
| Import endpoints/occ import | Bridge/import path | portability | Useful migration fallback, not a core product promise. |

### Recommendation

Deck is suitable as a low-friction bridge, fallback, or import path because it sits inside the existing Nextcloud stack. It should remain deferred until the provider-neutral model and backend adapter contract exist, and it must not define Release 1 navigation, module naming, or the normal Weave board UX.
